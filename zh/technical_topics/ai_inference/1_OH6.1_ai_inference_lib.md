# SpaceMIT K3 AI 推理库使用文档（llama.cpp C API / OpenHarmony 6.1 LTS）

面向第三方开发者，说明如何在 SpaceMIT K3平台的 OpenHarmony 6.1 LTS 设备上使用随系统预置的 llama.cpp 推理库，以及如何通过 ONNX Runtime + SpaceMIT EP 运行视觉模型：库清单、SpaceMIT 后端的使用方式、C API 用法与关键代码片段、命令行工具参数、HAP（ArkTS）集成方式与排障方法。

本文基于 **K3 + OpenHarmony 6.1 LTS** 实测整理。
K3 由 **8 个 X100 通用核 + 8 个 A100 AI 核** 组成。第三方开发无需了解具体硬件参数；若你的板卡或系统版本不同，请先用 `llama-cli --list-devices` 确认设备名与可用后端，再套用下文命令。


| 项目     | 内容                                                                                    |
| -------- | --------------------------------------------------------------------------------------- |
| 适用平台 | SpaceMIT K3+ OpenHarmony 6.1 LTS（API 23）                                              |
| 适用读者 | 需要在设备上用 C/C++ 或 ArkTS 集成 LLM / 视觉模型推理的第三方开发者                     |
| 推理栈   | llama.cpp（`libllama` / `libggml` + SpaceMIT 后端）；ONNX Runtime + SpaceMIT EP（视觉） |
| 库版本   | 系统预置库`build 51c81f90f (10056)`（下文所有性能数据均由该版本实测）                   |
| 文档版本 | v1.2                                                                                    |

> 文中标注 **实测** 的结论均已在该平台验证；标注 **说明** 的为接口语义或使用建议。性能数字见 3.5 节与第 6 章的示例。

## 1. 平台与运行时

### 1.1 运行环境说明

本文的命令、接口与日志均基于 **K3+ OpenHarmony 6.1 LTS** 实测。对第三方开发而言，需要关注的只有以下几点，其余硬件细节与你的业务无关：


| 关注点       | 说明                                                                                               |
| 设备名       | AI 加速器的 GGML 设备名固定为 `SPACEMIT0`（最新版库的启用方式见第 3 章）                          |
| 硬件构成     | K3 由 8 个 X100 通用核 + 8 个 A100 AI 核组成                                                       |
| 使用方式     | 设置 `GGML_SPACEMIT_BACKEND=1` 并指定 `--device SPACEMIT0`（见第 3 章）                            |
| 用户态       | musl libc，动态加载器`/lib/ld-musl-riscv64.so.1`；`/lib -> /system/lib`、`/lib64 -> /system/lib64` |
| 系统库目录   | `/system/lib64`（库）、`/system/bin`（命令行工具）                                                 |

后端启动时会向 stderr 打印一行初始化日志（`CPU_RISCV64_SPACEMIT: ...`），其中 `num_perfer_cores` 表示可参与推理的偏好核数量、`cpu_mask` 表示核掩码。这些值随板卡/系统配置变化，**不要把它写死到程序里**；需要绑核时用 `SPACEMIT_PERFER_CORE_ID`（见 3.4 与第 8 章）。

### 1.2 推理库清单

系统预置库位于 `/system/lib64`（**实测**，版本号随镜像版本变化，以实际安装为准）：


| 文件                    | 说明                                              |
| ----------------------- | ------------------------------------------------- |
| `libllama.so.0`         | llama.cpp 核心 C API（soname`libllama.so.0`）     |
| `libllama-common.so.0`  | 命令行工具公共层（参数解析、chat、采样封装等）    |
| `libmtmd.so.0`          | 多模态（mtmd）支持                                |
| `libggml.so.0`          | ggml 核心与调度器                                 |
| `libggml-base.so.0`     | ggml 基础层（张量、后端设备 API 等）              |
| `libggml-cpu.so.0`      | SpaceMIT 优化的基础后端（RVV/IME）                |
| `libggml-spacemit.so.0` | **SpaceMIT 加速后端**                             |
| `libonnxruntime.so`     | ONNX Runtime（视觉模型，见第 10 章）              |
| `libspacemit_ep.so`     | SpaceMIT Execution Provider（视觉模型加速）       |

`libllama.so.0` 的动态依赖（`readelf -d`）包含：

```
NEEDED  libggml.so.0
NEEDED  libggml-cpu.so.0
NEEDED  libggml-spacemit.so.0
NEEDED  libggml-base.so.0
NEEDED  libc.so
SONAME  libllama.so.0
```

也就是说 SpaceMIT 后端的动态库随 `libllama` 一起被加载，但**设备是否注册仍然受环境变量控制**（见第 3 章）。

> **链接注意**：运行时目录里通常只有带版本号的 `.so`（如 `libllama.so.0`），不一定有无版本号的 `libllama.so` 软链。因此“编译期用 SDK/头文件包里的软链目录链接、运行期按 soname 从 `/system/lib64` 解析”是标准做法；若没有软链，可用 `-l:libllama.so.0` 形式指定。

### 1.3 可执行文件与“启动器”机制

`/system/bin` 下与推理相关的可执行文件：


| 文件                                                                                                                                                   | 类型               |
| ------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------ |
| `llama-cli` / `llama-server` / `llama-bench` / `llama-batched-bench` / `llama-completion` / `llama-fit-params` / `llama-perplexity` / `llama-quantize` | 启动器（体积极小） |
| `llama-mtmd-cli` / `llama-embedding` / `llama-tokenize` / `llama-gguf-split`                                                                           | 独立可执行文件     |

**说明**：启动器（体积极小的那几个）自身只负责 `dlopen` 同名 `-impl.so` 并调用其入口。因此：

- 它们必须能访问 `/system/lib64`（同目录/系统库目录里的 `-impl.so` 缺一不可）；
- **不要**只把启动器拷贝到别处，缺失对应的 `-impl.so` 就无法运行；
- 通过 `hdc shell` 执行命令时，客户端常会打印 `[1][HH:MM:SS] Not support std mode`，这是 `hdc` 噪声，与推理库无关。

### 1.4 头文件与 ABI

C 接口头文件随 SDK / 源码包提供，典型布局（`llamacpp` 组件目录下）：

```
device/soc/spacemit/common/hardware/llamacpp/include/
device/soc/spacemit/common/hardware/llamacpp/lib/
```

关键头文件：`llama.h`、`ggml.h`、`ggml-backend.h`、`ggml-cpu.h`、`gguf.h`、`mtmd.h`；视觉模型另需 `onnxruntime_c_api.h` 与 `spacemit_ort_env_c_api.h`（见第 10 章）。

- ABI：ELF64 / musl，动态加载器 `/lib/ld-musl-riscv64.so.1`（与设备一致）；
- **第三方程序必须使用与本库同版本的头文件**，不要拿其它版本 llama.cpp 的 `llama.h` 混用，否则结构体布局不一致。

### 1.5 运行前准备

在设备 shell 中：

```sh
export PATH=/usr/bin:/bin:/system/bin
```

**说明**：应用沙箱或非交互 shell 里 `PATH` 可能不含 `/system/bin`；HAP 拉起子进程时同样要显式设置（见 7.2）。

## 2. 快速开始

三步走（均在设备 shell 中执行）：

```sh
# 1) 准备环境变量
export PATH=/usr/bin:/bin:/system/bin
export GGML_SPACEMIT_BACKEND=1          # 启用 SPACEMIT0 设备，供 --device 选择

# 2) 确认 SPACEMIT0 设备已注册
llama-cli --list-devices
# Available devices:
#   SPACEMIT0: Spacemit K3 AI Engine (<free> MiB, <total> MiB)

# 3) 跑一次基准（-dev 指定设备；llama-bench 的多设备分隔符是 "/"）
llama-bench -m /data/ai-infer/models/Qwen3-0.6B-Q4_0.gguf 
    -t 8 -p 128 -n 128 -fa 1 -ub 128 --load-mode mmap 
    -dev SPACEMIT0 -r 3
```

> 输出中括号内的两个数值是后端上报的**可用/总设备内存**，随板卡配置不同，与模型大小无关。

`llama-bench` 输出（**权威数据**：静默串行采集；`dev` 列显示所选设备名）：

```
| qwen3 0.6B Q4_0 | 358.78 MiB | 596.05 M | SPACEMIT | -1 | 8 | 128 | 1 | SPACEMIT0 | pp128 | 496.03 |
| qwen3 0.6B Q4_0 | 358.78 MiB | 596.05 M | SPACEMIT | -1 | 8 | 128 | 1 | SPACEMIT0 | tg128 |  41.06 |
```

> 上表为静默串行、`-r 3` 重复测量的**均值**（标准差从略）。

> 说明：`dev` 列显示所选设备的名称。**推荐同时给出 `GGML_SPACEMIT_BACKEND=1` 与 `--device SPACEMIT0`**，这样设备被正确选中且算子派发明确。

## 3. SpaceMIT 后端：设备注册与选择（重点）

K3 由 **8 个 X100 通用核 + 8 个 A100 AI 核** 组成。使用 SpaceMIT 后端的标准写法是**两者都给**：

```sh
export GGML_SPACEMIT_BACKEND=1   # 注册 SPACEMIT0 设备
--device SPACEMIT0               # 选中该设备
```

本章只讲这套用法。**环境变量只负责让设备出现在列表里**，它本身不是"开/关 AI 加速"的开关；
后端如何调度算子由库自身决定，开发者按本章方式配置即可，无需关心内部分配细节。

> 实践建议：始终把环境变量与 `--device` 一起给。只注册设备而不指定时，
> 算子派发不够明确，实测吞吐会低于指定设备的情形（`Qwen3-0.6B` 上 prefill 约 82%、decode 约 55%）。

### 3.1 注册并查看设备

```sh
export GGML_SPACEMIT_BACKEND=1
llama-cli --list-devices
```

输出：

```
Available devices:
  SPACEMIT0: Spacemit K3 AI Engine (<free> MiB, <total> MiB)
```

要点：

- 设备名固定为 **`SPACEMIT0`**；
- 括号内是后端上报的可用/总设备内存，**不是模型大小**；
- 该变量是**进程级**的，必须在启动进程前 `export`（HAP 里是在拉起的 shell 命令中设置，见 7.3）；
- 后端初始化时还会打印一行 `ggml-spacemit: ...` 的配置信息（worker 数、架构 id、向量长度等），属正常输出。

### 3.2 命令行用法

三个工具的参数名一致、**多设备分隔符不同**（**实测** `--help`）：

| 工具           | 参数                | 多设备分隔 | 示例                                                |
| -------------- | ------------------- | ---------- | --------------------------------------------------- |
| `llama-cli`    | `--device` / `-dev` | 逗号`,`    | `llama-cli -m model.gguf --device SPACEMIT0`        |
| `llama-server` | `--device` / `-dev` | 逗号`,`    | `llama-server -m model.gguf --device SPACEMIT0 ...` |
| `llama-bench`  | `--device` / `-dev` | 斜杠`/`    | `llama-bench -m model.gguf -dev SPACEMIT0`          |

**实测**完整命令：

```sh
export GGML_SPACEMIT_BACKEND=1
llama-cli -m /data/models/Qwen3-0.6B-Q4_0.gguf --device SPACEMIT0 
    -t 8 -c 4096 --reasoning off -st -n 24 
    -p "Introduce RISC-V in one sentence." < /dev/null
```

**实测**输出（节选，仅示意输出格式）：

```
> Introduce RISC-V in one sentence.
RISC-V is a widely adopted RISC architecture for development, target architecture, ...
[ Prompt: xx.x t/s | Generation: x.x t/s ]
Exiting...
```

> 在 `hdc`/应用等**非交互环境**中务必重定向 stdin（`< /dev/null`）或用 `-st`，否则 `llama-cli` 会等待输入、看起来"卡住"。本版本实测 `-no-cnv`（纯补全模式）从 stdin 读 prompt，配合 `-p` 不产出结果，一次性生成请用 `-st`。

**说明**：

- `--device SPACEMIT0` 只是选择设备；是否真正卸载还取决于 `-ngl`（`llama-bench`/`llama-cli` 默认 `-ngl -1`，即全部层卸载）；
- 也可用环境变量 `LLAMA_ARG_DEVICE=SPACEMIT0` 传递设备（`--help` 中标注 `(env: LLAMA_ARG_DEVICE)`）。

### 3.3 C API 用法：`llama_model_params.devices`

这是第三方程序指定加速设备的**唯一正确入口**。`llama.h` 中该字段定义（本版本）：

```c
struct llama_model_params {
    // NULL-terminated list of devices to use for offloading (if NULL, all available devices are used)
    ggml_backend_dev_t * devices;
    ...
    int32_t n_gpu_layers; // number of layers to store in VRAM, a negative value means all layers
    enum llama_load_mode  load_mode;
    ...
};
```

最小可用代码（完整片段见 6.2）：

```c
llama_backend_init();

struct llama_model_params params = llama_model_default_params();

/* devices 数组必须以 NULL 结尾，且生命周期覆盖 llama_model_load_from_file() */
static ggml_backend_dev_t devices[2] = { NULL, NULL };
ggml_backend_dev_t dev = ggml_backend_dev_by_name("SPACEMIT0");
if (dev != NULL) {
    devices[0] = dev;
    params.devices      = devices;
    params.n_gpu_layers = -1;   /* -1 = 全部层；也可以写具体层数 */
} else {
    fprintf(stderr, "未找到 SPACEMIT0；请先 export GGML_SPACEMIT_BACKEND=1\n");
}

struct llama_model * model = llama_model_load_from_file(path, params);
```

注意事项：

1. **`devices` 数组必须存活到模型加载完成**；不要传局部数组的地址后立刻返回。
2. `ggml_backend_dev_by_name()` 取不到设备时返回 `NULL`，必须判空并提示，不要静默继续。
3. `n_gpu_layers` 为负表示全部层；为 0 时即使指定设备也不会卸载。
4. 需要多设备时可放多个 `ggml_backend_dev_t`（以 `NULL` 结尾），本平台通常只用 `SPACEMIT0`。
5. 想确认设备是否生效，可检查 `ggml_backend_dev_name(dev)`，或观察模型加载后日志中的 `SPACEMIT compute buffer size`。

### 3.4 环境变量一览

**实测** 从系统库二进制的字符串表确认存在下列变量：

| 变量                        | 所在库                  | 取值/含义                                                                          | 建议                                           |
| --------------------------- | ----------------------- | ---------------------------------------------------------------------------------- | ---------------------------------------------- |
| `GGML_SPACEMIT_BACKEND`     | `libggml-spacemit.so.0` | `1` 启用/注册 `SPACEMIT0` 设备，使其可被 `--device`/`params.devices` 选中          | **设为 1**（推荐配置，见 3.1）                 |
| `GGML_SPACEMIT_FUSION`      | `libggml-spacemit.so.0` | 后端融合开关（二进制可见，未在公开文档给出语义）                                   | 默认不设置；调优时再试，并用`llama-bench` 验证 |
| `GGML_SPACEMIT_WORKERS`     | `libggml-spacemit.so.0` | 后端 worker 数量（同上）                                                           | 默认不设置                                     |
| `SPACEMIT_PERFER_CORE_ID`   | `libggml-cpu.so.0`      | 指定偏好核（逗号分隔的核编号；日志会打印`preferred core ids`，并做范围与架构校验） | 多路并行时用于绑核（见第 8 章）                |
| `SPACEMIT_PERFER_CORE_ARCH` | `libggml-cpu.so.0`      | 偏好核的架构 id                                                                    | 一般不需要                                     |
| `SPACEMIT_CORE_ARCH`        | `libggml-cpu.so.0`      | 覆盖检测到的 core arch                                                             | 一般不需要                                     |
| `SPACEMIT_MEM_BACKEND`      | `libggml-cpu.so.0`      | 内存后端（日志默认`HPAGE`）                                                        | 一般不需要                                     |
| `SPACEMIT_DISABLE_TCM`      | `libggml-cpu.so.0`      | 禁用 TCM 相关路径                                                                  | 排障时可试                                     |
| `GGML_CPU_DISABLE_FUSION`   | `libggml-cpu.so.0`      | 禁用该后端融合                                                                     | 排障时可试                                     |

**说明**：`GGML_SPACEMIT_*` 三个变量只在 `libggml-spacemit.so.0` 的字符串表中出现，官方头文件未声明其语义。日常使用只需 `GGML_SPACEMIT_BACKEND=1`，其余作为调优手段并自行基准验证。

### 3.5 运行参数与容量规划要点

以下来自设备实测，供容量规划参考（静默串行、`-p 128 -n 128 -r 3`）：

1. **后端吞吐几乎不随 `-t` 变化**：SpaceMIT 后端使用固定大小的 worker 池，`-t` 只影响配合线程。
   实测 `Qwen3.5-2B` 在 `-t` 1/2/4/8 下 PP 稳定在 133–134 tok/s、TG 稳定在 13.1–13.2 tok/s。
2. **`-t 1` 即可获得较高 prefill**，达到 8 个 X100 通用核全部投入时的量级。
   因此"只能分到 1–2 个核"的多路并发场景，用默认配置即可，不必把线程数拉满。
3. **不同模型表现差异明显**：小模型（≤1B）吞吐高、受固定开销影响；MoE 与 7B 以上模型
   需用 `llama-bench` 实测后再规划，不能一概而论。
4. **设备算力与内存带宽是独占资源**：同机并行第二路推理会显著拖慢第一路，
   测性能务必静默、单路、多跑 `-r`。

**配置建议**：

| 场景                                        | 建议                                                       |
| ------------------------------------------- | ---------------------------------------------------------- |
| 0.6B~1B 小模型、单路、可独占全部核          | 标准配置（`GGML_SPACEMIT_BACKEND=1` + `--device SPACEMIT0`）|
| 只能给推理分 1~2 个核（业务/UI 占用其余核） | 同上，`-t 1` 即可获得较高 prefill                          |
| 多路并发（每路 ≤4 核）                     | 按第 8 章绑核，每路设置不同的 `SPACEMIT_PERFER_CORE_ID`     |
| 7B 以上 / MoE / 长上下文大 batch prefill    | 先用 `llama-bench` 实测后规划                              |
| 视觉模型（ONNX）                            | 用 ONNX Runtime + SpaceMIT EP，见第 10 章                  |
| 与 UI 同机运行                              | 注意 DDR 带宽竞争：UI 高频刷新会显著拖慢推理（7.5 节有实测） |

## 4. C API 使用指南

本节接口原型均来自本版本 `llama.h` / `ggml-backend.h`。

### 4.1 生命周期

```
llama_backend_init()                       // 进程内一次；此后后端设备才可枚举
  │
  ├─ llama_model_default_params()
  ├─ [可选] ggml_backend_dev_by_name("SPACEMIT0") → params.devices
  ├─ llama_model_load_from_file(path, params)      // 加载模型
  │
  ├─ llama_context_default_params() → llama_init_from_model(model, params)
  ├─ llama_model_get_vocab(model)
  │
  ├─ llama_model_chat_template() → llama_chat_apply_template()   // 组装对话 prompt
  ├─ llama_tokenize()                                             // 文本 → token
  ├─ llama_batch_init() + llama_decode()                          // prefill
  ├─ llama_sampler_chain_init() → add(temp/top_k/top_p/dist)
  │
  └─ 生成循环 {
        llama_sampler_sample(smpl, ctx, -1)
        llama_vocab_is_eog(vocab, token) ? break
        llama_token_to_piece() → 输出
        llama_batch_get_one(&token, 1) + llama_decode()           // 单步增量
     }
     llama_sampler_free → llama_free → llama_model_free → llama_backend_free
```

### 4.2 模型加载参数

`struct llama_model_params` 关键字段：


| 字段                           | 类型                    | 说明                                                                            |
| ------------------------------ | ----------------------- | ------------------------------------------------------------------------------- |
| `devices`                      | `ggml_backend_dev_t *`  | NULL 结尾的设备数组；NULL 表示使用全部可用设备。指定设备时填`{SPACEMIT0, NULL}` |
| `n_gpu_layers`                 | `int32_t`               | 卸载到设备的层数；**负数表示全部层**，0 表示不卸载                              |
| `load_mode`                    | `enum llama_load_mode`  | `LLAMA_LOAD_MODE_NONE`(0) / `MMAP`(1) / `MLOCK`(2) / `DIRECT_IO`(3)；默认 mmap  |
| `split_mode`                   | `enum llama_split_mode` | 单设备时保持默认即可                                                            |
| `main_gpu`                     | `int32_t`               | 单设备主设备索引，默认 0                                                        |
| `tensor_split`                 | `const float *`         | 多设备按比例切分，单设备不用                                                    |
| `progress_callback`            | 函数指针                | 加载进度回调，返回 false 可中止加载                                             |
| `vocab_only` / `check_tensors` | `bool`                  | 只加载词表 / 校验张量                                                           |

命令行 `--load-mode` 的语义与之一一对应；旧的 `--no-mmap` 已被标记 deprecated，等价于 `--load-mode none`（**实测** `--help` 提示 "DEPRECATED in favor of `--load-mode`"）。

### 4.3 上下文参数

`struct llama_context_params` 关键字段：


| 字段                | 说明                                             | 建议取值                                           |
| ------------------- | ------------------------------------------------ | -------------------------------------------------- |
| `n_ctx`             | 上下文长度（token），0 = 取自模型                | 0.6B~4B：4096~15360；提示词很长时 15360            |
| `n_batch`           | 逻辑批上限                                       | 512                                                |
| `n_ubatch`          | 物理批上限                                       | 128（与 bench 一致；越大越吃内存）                 |
| `n_seq_max`         | 最大并行序列数                                   | 单路对话 1                                         |
| `n_threads`         | 生成阶段 CPU 线程数                              | 按可用核数设置（如 4~8）                           |
| `n_threads_batch`   | 预填充阶段线程数                                 | 与`n_threads` 相同                                 |
| `flash_attn_type`   | Flash Attention：AUTO(-1)/DISABLED(0)/ENABLED(1) | 默认 AUTO（实测运行日志`Flash Attention enabled`） |
| `type_k` / `type_v` | KV cache 量化类型                                | 默认 f16；内存紧张时试 q8_0                        |
| `offload_kqv`       | 是否把 KQV 算子（含 KV cache）卸载到设备         | 默认 true                                          |
| `embeddings`        | 是否输出 embedding                               | 普通对话 false                                     |

**说明**：请求值不一定等于实际生效值，创建上下文后应读取 `llama_n_ctx()` / `llama_n_batch()` / `llama_n_ubatch()` 确认。

### 4.4 chat template 与分词

```c
/* 取模型内置模板；模型没带模板时返回 NULL */
const char * tmpl = llama_model_chat_template(model, NULL);

/* 按模板拼 prompt；返回值是“完整结果所需字节数”，
   大于 buf 容量时需要扩容后重试（建议按 2 倍消息总字符数分配） */
int32_t llama_chat_apply_template(
        const char * tmpl,
        const struct llama_chat_message * chat,   /* {role, content} 数组 */
        size_t n_msg,
        bool add_ass,                             /* 是否以 assistant 起始标记结尾 */
        char * buf,
        int32_t length);
```

分词：

```c
int32_t llama_tokenize(
    const struct llama_vocab * vocab,
    const char * text, int32_t text_len,
    llama_token * tokens, int32_t n_tokens_max,
    bool add_special,     /* 是否允许加 BOS/EOS */
    bool parse_special);  /* 是否把 <|im_start|> 之类识别为特殊 token */
```

**返回值语义（重要）**：成功返回 token 数；缓冲区不足返回**负数**，其绝对值就是所需 token 数。因此标准用法是“先传 `NULL, 0` 探长度，再分配，再第二次调用”（见 6.4）。

实践建议：

- 用了 chat template 时，模板输出里已包含特殊 token，`add_special` 传 `false`、`parse_special` 传 `true`，避免重复 BOS；
- 纯文本续写（不用模板）时 `add_special = true`；
- 词表大小用 `llama_vocab_n_tokens(vocab)` 获取。

### 4.5 批处理与 llama_decode

`struct llama_batch` 是“批”的描述结构，包含 `n_tokens / token / embd / pos / n_seq_id / seq_id / logits`。三种构造方式：


| 方式                                          | 用途                                                              | 是否需`llama_batch_free` |
| --------------------------------------------- | ----------------------------------------------------------------- | ------------------------ |
| `llama_batch_get_one(tokens, n)`              | 快速单序列批（**视图**，`token` 指向调用者内存，其余指针为 NULL） | **否**（见下方警告）     |
| `llama_batch_init(n_tokens, embd, n_seq_max)` | 堆上分配、逐字段填写（适合完整控制 pos/seq_id/logits）            | **是**                   |
| 手工填结构体                                  | 特殊场景                                                          | 自行管理                 |

`llama_decode(ctx, batch)` 返回 0 成功、非 0 失败；每次 decode 前必须保证上下文剩余空间（`n_ctx`）足够。

> ⚠️ **实测确认的坑：不要对 `llama_batch_get_one()` 返回的批调用 `llama_batch_free()`。**
>
> 反汇编 `libllama.so.0` 的 `llama_batch_free` 可见：它依次检查结构体中偏移 8/16/24/32/40/48 的指针（即 `token/embd/pos/n_seq_id/seq_id[]/logits`），**每个非空指针都会直接 `free()`**。而 `llama_batch_get_one()` 只是把这些字段填成调用者的指针（`token` 指向你的数组，其余为 NULL）。若对单 token 增量批（`llama_batch_get_one(&id, 1)`）调用释放函数，就会 `free()` 一个栈地址，进程崩溃。
>
> 结论：**`llama_batch_init` ↔ `llama_batch_free` 成对；`llama_batch_get_one` 的批用完直接丢弃。**

`logits` 语义：`logits[i] = 1` 表示需要该位置输出；`llama_batch_get_one` 的 `logits == NULL`，此时实现只在最后一个位置输出 logits，所以 `llama_sampler_sample(smpl, ctx, -1)` 取 `-1`（最后一个输出）即可。

### 4.6 采样链

```c
struct llama_sampler_chain_params sparams = llama_sampler_chain_default_params();
struct llama_sampler * smpl = llama_sampler_chain_init(sparams);

llama_sampler_chain_add(smpl, llama_sampler_init_temp(0.7f));
llama_sampler_chain_add(smpl, llama_sampler_init_top_k(40));
llama_sampler_chain_add(smpl, llama_sampler_init_top_p(0.95f, 1));
llama_sampler_chain_add(smpl, llama_sampler_init_dist(42));   /* seed */

/* 每步采样；内部会 accept 选中的 token，无需再调 llama_sampler_accept */
llama_token id = llama_sampler_sample(smpl, ctx, -1);
```

**说明**：

- 顺序与 llama.cpp 默认一致：`temp → top_k → top_p → dist`；最后一个必须是“选择型”采样器（`dist` 或 `greedy`）；
- `llama_sampler_chain_add()` 会**接管所有权**，chain 释放时自动释放成员，**不要**再单独 free 成员；
- 需要确定性输出时把 `temp` 设很小或直接用 `llama_sampler_init_greedy()`；
- `llama_sampler_sample` 返回的 token 可直接送 `llama_vocab_is_eog()` 判断是否结束（Qwen 系列的 `<|im_end|>` 等会被识别）。

### 4.7 token 到文本（流式输出）

```c
int32_t llama_token_to_piece(
        const struct llama_vocab * vocab,
        llama_token token,
        char * buf, int32_t length,
        int32_t lstrip,      /* 跳过开头的空格数 */
        bool special);       /* 是否渲染特殊 token */
```

- 成功返回写入字节数；缓冲区不足返回**负数**（绝对值为所需长度）；
- 不写 `\0`，输出后自行 `fwrite`；
- **说明**：一个 token 的字节序列可能是 UTF-8 字符的一部分，流式输出时若要做“逐字上屏”，应先拼接再按完整 UTF-8 码点切分，或整段缓冲后刷新（HAP 中即按 60ms 合并下发，见 7.5）。

### 4.8 资源释放

正确顺序（按此顺序释放不会泄漏）：

```c
llama_sampler_free(smpl);    /* 采样链（连带其成员） */
llama_free(ctx);             /* 上下文 */
llama_model_free(model);     /* 模型 */
llama_backend_free();        /* 进程级后端（可选，退出前调用） */
```

常见泄漏/错误：

- `llama_batch_init` 后未 `llama_batch_free`；
- 对 `llama_batch_get_one` 的批误调 `llama_batch_free`（会崩溃，见 4.5）；
- 采样器成员被单独 free 后又被 chain free（双重释放）；
- 只 `llama_free(ctx)` 忘记 `llama_model_free(model)`（模型占用最大，必须释放）。

### 4.9 设备枚举与内存信息

来自 `ggml-backend.h`：

```c
size_t             n = ggml_backend_dev_count();
ggml_backend_dev_t d = ggml_backend_dev_get(i);
const char *      name = ggml_backend_dev_name(d);
const char *      desc = ggml_backend_dev_description(d);
enum ggml_backend_dev_type t = ggml_backend_dev_type(d);
size_t free_mem = 0, total_mem = 0;
ggml_backend_dev_memory(d, &free_mem, &total_mem);

ggml_backend_dev_t picked = ggml_backend_dev_by_name("SPACEMIT0");  /* 关键入口 */
```

设备类型枚举：`GGML_BACKEND_DEVICE_TYPE_CPU / GPU / IGPU / ACCEL / META`。`SPACEMIT0` 为加速设备（非 CPU 类型），程序应据此决定是否卸载。

### 4.10 日志控制

后端加载/调度会向 stderr 打印大量 INFO（例如每步 `ggml-spacemit: SPACEMIT0 graph-compute n_nodes ...`），与业务输出混在一起。可用：

```c
void llama_log_set(ggml_log_callback log_callback, void * user_data);
/* 传 NULL 回调则恢复默认（全部输出到 stderr）；logger 状态是全局的，非线程安全 */
```

**说明**：应用里建议安装自定义回调，按级别过滤后转发到 `hilog`，避免子进程 stderr 阻塞或刷屏。

### 6.2 片段 1：初始化后端并选择 SPACEMIT0

**这段在做什么**：启动 ggml 后端，按名字取加速设备，把 `{SPACEMIT0, NULL}` 填进模型参数；设备取不到时给出提示并按默认方式加载。

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

#include "llama.h"
#include "ggml-backend.h"

static ggml_backend_dev_t g_devices[2] = { NULL, NULL };  /* 必须 NULL 结尾 */

/* 返回实际使用的设备；NULL 表示使用 CPU */
static ggml_backend_dev_t pick_device(const char * want)
{
    ggml_backend_dev_t dev = (want && *want) ? ggml_backend_dev_by_name(want) : NULL;
    if (dev == NULL) {
        fprintf(stderr, "[warn] 未找到设备 %s，回退 CPU；"
                        "若要用加速设备请先 export GGML_SPACEMIT_BACKEND=1\n",
                want ? want : "(null)");
        return NULL;
    }
    if (ggml_backend_dev_type(dev) == GGML_BACKEND_DEVICE_TYPE_CPU) {
        fprintf(stderr, "[warn] 设备 %s 是 CPU 类型，不卸载\n", want);
        return NULL;
    }
    return dev;
}
```

**关键点**：

- `llama_backend_init()` 要在枚举设备**之前**调用（进程内一次即可）；
- `g_devices` 必须是 **static / 堆上**的，数组以 `NULL` 结尾，且**生命周期覆盖 `llama_model_load_from_file()`**；
- 未设置 `GGML_SPACEMIT_BACKEND=1` 时 `ggml_backend_dev_by_name("SPACEMIT0")` 返回 `NULL`，设备取不到就无法作为卸载目标；这是最常见的配置遗漏。

### 6.3 片段 2：加载模型与创建上下文

**这段在做什么**：用上一步选出的设备加载 GGUF，再按需创建上下文。

```c
llama_backend_init();

struct llama_model_params mparams = llama_model_default_params();
ggml_backend_dev_t dev = pick_device("SPACEMIT0");
if (dev != NULL) {
    g_devices[0]        = dev;
    mparams.devices     = g_devices;   /* NULL 结尾的设备数组 */
    mparams.n_gpu_layers = -1;         /* -1 = 全部层卸载 */
}

struct llama_model * model = llama_model_load_from_file(path, mparams);
if (model == NULL) { fprintf(stderr, "加载模型失败: %s\n", path); return 1; }

struct llama_context_params cparams = llama_context_default_params();
cparams.n_ctx           = 4096;   /* 上下文长度，按业务需要调整 */
cparams.n_batch         = 512;
cparams.n_ubatch        = 128;
cparams.n_threads       = 8;      /* 生成阶段线程数，按可用核数调整 */
cparams.n_threads_batch = 8;      /* prefill 阶段线程数 */

struct llama_context * ctx = llama_init_from_model(model, cparams);
const struct llama_vocab * vocab = llama_model_get_vocab(model);
```

**关键点**：

- `n_gpu_layers` 只有在**负数（通常 -1）**时才全量卸载；写 0 等于选了设备也不用；
- 请求值不保证生效，可再用 `llama_n_ctx(ctx)` / `llama_n_batch(ctx)` 打印实际值；
- 指定设备后日志会出现 `SPACEMIT compute buffer size ...`，这是“确实卸载成功”的最直接证据；
- 线程数按“能分给推理的核数”设置（见 3.5：后端吞吐几乎不随 `-t` 变化）。

### 6.4 片段 3：组装对话 prompt 并分词

**这段在做什么**：取模型内置的 chat 模板拼出对话 prompt，再把它转成 token 序列。

```c
struct llama_chat_message msg[] = {
    { "system", "You are a helpful assistant." },
    { "user",   "用一句话介绍 RISC-V" },
};
const int n_msg = (int)(sizeof(msg) / sizeof(msg[0]));

/* 1) 套模板；返回值为“完整结果所需字节数”，不够就扩容重试 */
const char * tmpl = llama_model_chat_template(model, NULL);
int32_t need = llama_chat_apply_template(tmpl, msg, n_msg, true, NULL, 0);
char * prompt = (char *)malloc((size_t)need + 1);
llama_chat_apply_template(tmpl, msg, n_msg, true, prompt, need + 1);

/* 2) 分词：先探长度（返回负数 = 所需 token 数），再分配 */
int32_t n_tok = -llama_tokenize(vocab, prompt, (int32_t)strlen(prompt), NULL, 0, false, true);
llama_token * toks = (llama_token *)malloc(sizeof(llama_token) * (size_t)n_tok);
n_tok = llama_tokenize(vocab, prompt, (int32_t)strlen(prompt), toks, n_tok, false, true);
if (n_tok < 0) { fprintf(stderr, "分词失败\n"); return 1; }
```

**关键点**：

- `llama_chat_apply_template()` 与 `llama_tokenize()` 的返回值都是“**需要多大**”，缓冲区不足时返回**负数**，所以要“先探长度再分配”；
- 用了模板时 `add_special = false`（模板里已含特殊 token），`parse_special = true`（识别 `<|im_start|>` 之类）；
- 模型自带模板时 `llama_model_chat_template(model, NULL)` 返回该模板，返回 `NULL` 时应改用纯文本拼接。

### 6.5 片段 4：prefill 与采样链

**这段在做什么**：把整段 prompt 一次性喂给模型（prefill），并构造 `temp → top_k → top_p → dist` 采样链。

```c
/* 1) prefill：llama_batch_init 分配的批必须配对 llama_batch_free */
struct llama_batch batch = llama_batch_init((int32_t)n_tok, 0, 1);
for (int32_t i = 0; i < n_tok; i++) {
    batch.token[i]      = toks[i];
    batch.pos[i]        = i;
    batch.n_seq_id[i]   = 1;
    batch.seq_id[i][0]  = 0;
    batch.logits[i]     = (i == n_tok - 1) ? 1 : 0;  /* 只需要最后一个位置出 logits */
}
batch.n_tokens = n_tok;
if (llama_decode(ctx, batch) != 0) { fprintf(stderr, "prefill 失败\n"); return 1; }
llama_batch_free(batch);          /* 与 llama_batch_init 配对 */

/* 2) 采样链：顺序为 temp -> top_k -> top_p -> dist */
struct llama_sampler * smpl =
    llama_sampler_chain_init(llama_sampler_chain_default_params());
llama_sampler_chain_add(smpl, llama_sampler_init_temp(0.7f));
llama_sampler_chain_add(smpl, llama_sampler_init_top_k(40));
llama_sampler_chain_add(smpl, llama_sampler_init_top_p(0.95f, 1));
llama_sampler_chain_add(smpl, llama_sampler_init_dist(LLAMA_DEFAULT_SEED));
```

**关键点**：

- `llama_batch_init()` 分配的批**必须**用 `llama_batch_free()` 释放（与 6.6 的 `get_one` 视图相反）；
- `logits[i] = 1` 表示需要该位置输出；只把最后一个位置设为 1 最省内存；
- 采样链**最后一个必须是选择型采样器**（`dist` 或 `greedy`），否则采样无输出；
- `llama_sampler_chain_add()` 接管所有权，chain 释放时会连同成员一起释放。

### 6.6 片段 5：一次完整推理循环

**这段在做什么**：从当前上下文采样下一个 token，输出到终端，再把它解码回上下文，循环到结束 token 或长度上限。

```c
const int n_predict = 256;
char piece[256];

for (int i = 0; i < n_predict; i++) {
    /* 采样：内部已 accept 该 token，不要再手动 accept */
    llama_token id = llama_sampler_sample(smpl, ctx, -1);
    if (llama_vocab_is_eog(vocab, id)) break;          /* EOS / <|im_end|> 等 */

    /* token -> 文本：返回负数表示缓冲不够（绝对值 = 所需字节数） */
    int32_t n = llama_token_to_piece(vocab, id, piece, (int32_t)sizeof(piece), 0, true);
    if (n > 0) fwrite(piece, 1, (size_t)n, stdout), fflush(stdout);

    /* 单步增量解码：get_one 返回的是“视图”，用完不要 free */
    struct llama_batch one = llama_batch_get_one(&id, 1);
    if (llama_decode(ctx, one) != 0) { fprintf(stderr, "decode 失败\n"); break; }
}
```

**关键点**：

- `llama_sampler_sample()` 内部会 accept 选中的 token，**不需要再调** `llama_sampler_accept()`；
- `llama_batch_get_one()` 返回的是**视图**（`token` 指向你的变量），**绝不能**传给 `llama_batch_free()`，否则会 `free()` 栈地址导致崩溃（见 4.5）；
- 增量解码时位置（`pos`）由上下文自动推进，无需手动维护；
- 流式输出要 `fflush(stdout)`，否则看起来像卡住。

### 6.7 片段 6：资源释放

**这段在做什么**：按依赖顺序释放所有资源。

```c
llama_sampler_free(smpl);   /* 采样链（连同成员） */
free(toks); free(prompt);   /* 自己 malloc 的缓冲 */
llama_free(ctx);            /* 上下文 */
llama_model_free(model);    /* 模型（占用最大，必须释放） */
llama_backend_free();       /* 进程级后端，退出前调用 */
```

**关键点**：顺序要与创建顺序相反；只 `llama_free(ctx)` 而忘记 `llama_model_free(model)` 是最常见的内存泄漏。

#### 交叉编译（设备端可执行文件）

用 SpaceMIT 的 OHOS musl 工具链（目录名形如 `spacemit-toolchain-linux-musl-x86_64-oh-*`）：

```sh

```

链接参数说明（踩坑记录）：


| 写法                              | 结果                                                                                                                      |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `-lllama -lggml`                  | **不够**：`ggml_backend_dev_memory` 等符号在 `libggml-base`，会报 `undefined reference ... DSO missing from command line` |
| `-lllama -lggml -lggml-base`      | ✅ 推荐，覆盖示例用到的全部符号                                                                                           |
| 追加`-Wl,-rpath-link,"$LIB"`      | 让链接器沿`libllama.so.0` 的 `NEEDED` 链解析依赖                                                                          |
| 追加`-Wl,--allow-shlib-undefined` | 必需：`libggml-cpu` / `libggml-spacemit` 依赖运行时的 `libspert.so.1`，不在链接路径中                                     |

**说明**：

- 运行时目录里可能只有 `libllama.so.0` 这种带版本号的库，此时把 `-lllama` 换成 `-l:libllama.so.0`（其余同理）；
- 交叉编译产物默认 rpath 为空，运行时需 `LD_LIBRARY_PATH=/system/lib64:/system/lib`；随 HAP 打包时建议加 `-Wl,-rpath,'$ORIGIN'`，让程序从自身 `libs/<abi>` 目录加载；
- 链接期出现 `warning: libspert.so.1 ... not found` 属正常（运行时由系统库目录提供）。

**实测** 运行输出形态：


带 `GGML_SPACEMIT_BACKEND=1 --device SPACEMIT0` 时，日志会出现 `~llama_context: SPACEMIT compute buffer size is ...`（证明张量确实在加速设备上），并可见逐步 `ggml-spacemit: SPACEMIT0 graph-compute n_nodes ...`。

### 6.9 关键点回顾

1. 先 `llama_backend_init()`，再枚举设备/取 `SPACEMIT0`；
2. `devices` 数组 NULL 结尾、生命周期覆盖模型加载；
3. `n_gpu_layers = -1` 才会全量卸载；
4. `llama_batch_init ↔ llama_batch_free`，`get_one` 视图**不可** free；
5. `llama_tokenize`/`llama_token_to_piece` 的负数返回是“所需长度”；
6. `llama_sampler_sample` 已内部 accept，不要重复 accept；
7. 设备卸载需要三项配合：`GGML_SPACEMIT_BACKEND=1`（注册设备）+ `params.devices`/`--device SPACEMIT0`（选中设备）+ `n_gpu_layers=-1`（允许全层卸载）。

## 7. HAP（ArkTS）集成

以下命令与结论来自开源项目 **llmchat**（[https://gitee.com/spacemit-openharmony/llmchat](https://gitee.com/spacemit-openharmony/llmchat)，main 分支），可直接作为参考实现。

### 7.1 架构

```
ArkTS UI (EntryAbility / Index.ets)
   │  ① 启动时 spawn 一条 shell 命令拉起 llama-server（仅 1 个常驻子进程）
   ▼
llama-server（监听 127.0.0.1:8080，OpenAI 兼容）
   ▲
   │  ② @ohos.net.http：GET /health 探活；POST /v1/chat/completions（stream=true）取 SSE
   │
ArkTS（LlamaService.ets）→ 按 60ms 合并增量 → UI 更新
```

要点：**只有“拉起 llama-server”这一次需要 `process.runCmd`/`spawn`**；健康检查与对话流全部走 `@ohos.net.http`（进程内，不产生子进程）。

### 7.2 拉起 llama-server

**基础命令（实测）**，来自 llmchat 的 `EntryAbility.ets`：

```ts
const command =
  `pkill -9 llama-server; sleep 1; ` +
  `export PATH=/usr/bin:/bin:/system/bin; ` +
  `exec llama-server -m ${this.modelPath} -t 4 --host 127.0.0.1 --port 8080 ` +
  `--ctx-size 15360 --batch-size 512 --metrics --no-mmap --reasoning off`;
this.llamaServerProcess = spawn(command);   // spawn = process.runCmd + 持有引用（ChildProcessGuard）
```

设计要点：

- **`pkill + sleep + exec` 合并在同一条命令里**：`exec` 让中间的 `sh` 退场，只留一个常驻的 `llama-server` 子进程；
- `--ctx-size 15360`：上层应用会复用该服务，提示词含大量工具定义 + RAG 上下文（实测约 5192 token），4096 会直接 `exceed_context_size_error`；
- `--reasoning off`：Qwen3.5 等思考模型不加会把 token 预算烧在 `reasoning_content` 上、`content` 为空；
- `--no-mmap`：模型在应用沙箱，禁用 mmap 更稳（新版本建议等价写 `--load-mode none`）。

### 7.3 指定加速设备的改造

在原有命令基础上增加两处：**`export GGML_SPACEMIT_BACKEND=1`** 与 **`--device SPACEMIT0`**。

完整改造后命令：

```ts
const command =
  `pkill -9 llama-server; sleep 1; ` +
  `export PATH=/usr/bin:/bin:/system/bin; ` +
  `export GGML_SPACEMIT_BACKEND=1; ` +
  `exec llama-server -m ${this.modelPath} -t 4 --host 127.0.0.1 --port 8080 ` +
  `--ctx-size 15360 --batch-size 512 --metrics --no-mmap ` +
  `--reasoning off --device SPACEMIT0`;
this.llamaServerProcess = spawn(command);
```

**实测等价命令**（在设备 shell 中直接执行同一串，`--port 8099` 只是避开占用）：

```
GET  /health              → {"status":"ok"}
POST /v1/chat/completions → 正常返回 content
日志                      → srv  llama_server: listening on http://127.0.0.1:8099
```

ArkTS 片段（`EntryAbility.launchLlamaServer()` 改造版）：

```ts
import { process } from '@kit.ArkTS';
import { spawn } from '../service/ChildProcessGuard';

private launchLlamaServer(): void {
  try {
    // 1) 原命令的 pkill/sleep/exec 结构保持不变（避免 FFRT 线程池被短命子进程占满）
    // 2) 新增 GGML_SPACEMIT_BACKEND=1 与 --device SPACEMIT0 指定加速设备
    const command =
      `pkill -9 llama-server; sleep 1; ` +
      `export PATH=/usr/bin:/bin:/system/bin; ` +
      `export GGML_SPACEMIT_BACKEND=1; ` +
      `exec llama-server -m ${this.modelPath} -t 4 --host 127.0.0.1 --port 8080 ` +
      `--ctx-size 15360 --batch-size 512 --metrics --no-mmap ` +
      `--reasoning off --device SPACEMIT0`;
    hilog.info(0x0000, 'testTag', `Launching: ${command}`);

    // 子进程存活期间必须一直被引用：ChildProcess 不可达时 NAPI finalizer 会同步 waitpid
    // 卡死主线程（详见 ChildProcessGuard.ets 注释）
    this.llamaServerProcess = spawn(command);
  } catch (err) {
    hilog.error(0x0000, 'testTag', `Launch failed: ${JSON.stringify(err)}`);
  }
}
```

**说明**：

- 设备名不被识别时，`llama-server` 会忽略未知设备继续启动、不会失败；建议启动前后都用 `llama-cli --list-devices` 确认 `SPACEMIT0` 已出现；
- 若想省去设备选择、只用默认调度，删掉 `--device SPACEMIT0` 与 `GGML_SPACEMIT_BACKEND=1` 即可；
- 需要绑核/多路时再加 `SPACEMIT_PERFER_CORE_ID`（见第 8 章）；
- 应用内调试可看 `hilog` 中 `Launching:` 行，确认环境变量确实拼进了命令。

### 7.4 与 server 通信

使用 `@kit.NetworkKit` 的 `http`：

```ts
import { http } from '@kit.NetworkKit';

// 探活：GET /health → {"status":"ok"}；503 表示模型仍在加载
const request = http.createHttp();
const resp = await request.request('http://127.0.0.1:8080/health', {
  method: http.RequestMethod.GET,
  connectTimeout: 3000,
  readTimeout: 3000,
  usingCache: false,
});

// 对话：POST /v1/chat/completions，stream=true 取 SSE
// 关键：必须用 requestInStream()，普通 request() 会把响应体攒完一次性返回
await request.requestInStream('http://127.0.0.1:8080/v1/chat/completions', {
  method: http.RequestMethod.POST,
  header: { 'Content-Type': 'application/json' },
  extraData: JSON.stringify({ model: modelPath, messages, stream: true, temperature: 0.7, max_tokens: 2048 }),
  connectTimeout: 5000,
  readTimeout: 600000,
  usingCache: false,
});
request.on('dataReceive', (chunk: ArrayBuffer) => {
  // 按行切 SSE：data: {...} / data: [DONE]
  // 取 choices[0].delta.content 追加到缓冲
});
```

解析要点：

- 按 `\n` 切行，保留最后一段不完整行；
- `data: [DONE]` 表示结束；
- 只取 `choices[0].delta.content`（思考模型关掉 reasoning 后不会再有 `reasoning_content` 干扰）；
- 服务端 `timings` 字段可用于对账（`prompt_ms`、`predicted_per_second`）。

### 7.5 五条硬经验

以下均为 llmchat 实测得到的结论，**务必遵守**，否则会出现“命令行 10.5 tok/s、应用内 0.4 tok/s”这类 20 倍差距。

#### ① 不要用 `process.runCmd`/curl 子进程做健康检查和对话取流

每 spawn 一个子进程，ArkTS 运行时就在 **FFRT 线程池**上留一个读其 stdout 的异步任务（栈：`ChildProcess::ReadStdOut ← NativeAsyncWork`）。该任务不随子进程退出而释放，会持续空转；池子大小与核数相关。攒满后：

- 应用进程常态烧 **600%~800% CPU**；
- 同机 `llama-server` 被饿死，实测同一模型同一参数：**命令行拉起 10.5 tok/s，应用内只有 0.4 tok/s**；
- 界面表现：首字很慢 + 长时间卡顿。

因此：**健康检查与对话流走 `@ohos.net.http`（纯进程内，无子进程）**，只有拉起 `llama-server` 那一次才 spawn。

#### ② 拉起命令里用 `exec`，只保留一个常驻子进程

`pkill -9 llama-server; sleep 1; export ...; exec llama-server ...` 合成一条命令：`pkill` 段执行完后 `exec` 顶替成 `llama-server`，整个过程只有 1 个子进程且一直活着，读 stdout 的任务永远处于阻塞态（不耗 CPU）。

另外：`ChildProcess` 对象在子进程存活期间**必须一直持有引用**，否则 NAPI finalizer 会在主线程同步 `waitpid()`，把 UI 卡死（实测冻结 20s 以上，被 FreezeDetector 判 `THREAD_BLOCK_6S`）。子进程退出后 `pid` 会变成垃圾值，**不要拿它做 kill 句柄**，按名字 `pkill` 收尾。

#### ③ 模型必须放应用沙箱 `context.filesDir`

- 系统分区空间有限且通常接近写满，放不下几百 MB 的模型；
- 沙箱路径：`/data/app/el2/<userid>/base/<bundle>/haps/entry/files/model.gguf`（`context.filesDir` 的物理映射）；
- 应用内可用 `fs.statSync(modelPath)` 预检，不存在时给 UI 明确提示。

#### ④ 思考模型要加 `--reasoning off`

Qwen3.5 等模型默认会先输出 `reasoning_content`。实测不加时 512 个 token 全被 reasoning 吃掉、`content` 为空（界面空白气泡）；加 `--reasoning off` 后同一问题 2 个 token 直接给出答案。

#### ⑤ UI 输出节奏也会拖慢推理

原实现 30ms 吐 1 字（33 字/秒）导致：英文约 5 字符/token，10 tok/s 就是 50 字/秒，队列永远追不上；每秒 33 次 UI 落字 + 滚屏让应用常态吃 130% CPU，占满部分核，`llama-server` 从 10.3 tok/s 掉到 5.3 tok/s（推理是访存密集，渲染抢同一份 DDR 带宽）。

现做法：**同一时间窗增量合并，60ms 刷新一次 UI**，节奏与命令行一致。

### 7.6 模型部署

**不要把模型直接推到应用沙箱目录**。推荐做法是：先把模型推到 `data` 分区，
再在沙箱目录里建立**硬链接**指向它。这样做的原因：

- 沙箱目录容量与配额受限，动辄数 GB 的 GGUF 直接推动辄失败或被系统清理；
- 同一模型可被多个应用共享，只需一次推送；
- 硬链接不占额外空间（与源文件共用同一份数据），删除链接也不影响源文件。

流程：

```sh
# 1) 推模型到 data 分区（有独立且充足的空间）
hdc shell "mkdir -p /data/models"
hdc file send model.gguf /data/models/model.gguf
hdc shell "ls -l /data/models/model.gguf"      # 校验大小

# 2) 查包名与沙箱路径（示例包名 com.example.llmchat）
hdc shell "ls /data/app/el2/100/base/com.example.llmchat/haps/entry/files/"

# 3) 在沙箱目录建立指向 data 分区的硬链接
hdc shell "ln /data/models/model.gguf \
  /data/app/el2/100/base/com.example.llmchat/haps/entry/files/model.gguf"

# 4) 校验链接（应与源文件同 inode、同大小）
hdc shell "ls -li /data/models/model.gguf \
  /data/app/el2/100/base/com.example.llmchat/haps/entry/files/model.gguf"
```

第 4 步两个路径的 **inode 号必须相同**，这是硬链接建立成功的判据。

> 硬链接**不能跨文件系统**。若 `ln` 报 `Invalid cross-device link`，说明沙箱目录与 `/data/models`
> 不在同一分区，此时退化为软链接（`ln -s /data/models/model.gguf <沙箱路径>`），
> 但必须保证源文件不会被清理。
>
> 也可以先把模型推到沙箱**同分区**的公共目录，再建硬链接，避免跨分区问题。

应用内代码：

```ts
import fs from '@ohos.file.fs';
const modelPath = `${this.context.filesDir}/model.gguf`;
try {
  fs.statSync(modelPath);       // 存在（硬链接对应用透明，按普通文件访问）
} catch (_) {
  // 不存在：提示用户导入模型
}
```

**说明**：沙箱路径与 `context.filesDir` 的映射关系随包名/用户 id 变化，生产环境应以 `context.filesDir` 为准，不要硬编码。硬链接建立后，应用访问 `modelPath` 与访问普通文件完全一致。

### 7.7 生命周期与收尾

- 拉起：`onCreate` 中 `fs.stat` 校验模型 → `setTimeout(() => startLlamaServer(), 100)`；
- 健康检查：UI 启动后轮询 `GET /health`（间隔 1~2s，带超时），`{"status":"ok"}` 才允许对话；
- 销毁：`onDestroy` 里 `pkill -9 llama-server` 收尾（同样走 spawn，但只发短命令，拿到输出后释放对象）；
- 推理资源残留：轻量发行版上通常**没有** `spacemit-tcm-smi` 之类的清理工具，异常退出后靠 `pkill` 清理；无法清理时重启设备。

### 7.8 权限

- 访问 `127.0.0.1:8080` 同样需要网络权限：在 `module.json5` 声明 `ohos.permission.INTERNET`；
- 若模型放在公共目录读取，还需相应用户文件权限；放沙箱 `filesDir` 则无需额外权限。

## 8. 多路推理与绑核

AI 加速器是**独占资源**：同一时刻多路抢同一批核会导致**两路都异常**。

依据见 3.5：**后端吞吐不随 `-t` 变化**（worker 池固定）；给推理分不到足够核时，`-t 1` 即可获得较高 prefill，因此多路场景应采用“每路绑不同核 + 小 `-t`”。

### 8.1 单路

```sh
export GGML_SPACEMIT_BACKEND=1
llama-cli -m model.gguf --device SPACEMIT0 -t 8 ...
```

`-t 8` 让 CPU 侧配合线程也拉满；AI 阵列的并行度由后端固定，单路 AI 推理调小 `-t` 对吞吐影响很小（见 3.5），只有多路绑核时才需按每路分到的核数设置。

### 8.2 双路（按核分组绑核）

绑核通过 `SPACEMIT_PERFER_CORE_ID` 指定（日志会打印 `preferred core ids`，并对范围/架构做校验）：

```sh
# 终端 1：绑定第一组核
export SPACEMIT_PERFER_CORE_ID="8,9,10,11"
export GGML_SPACEMIT_BACKEND=1
llama-cli -m modelA.gguf --device SPACEMIT0 -t 4 ...

# 终端 2：绑定第二组核
export SPACEMIT_PERFER_CORE_ID="12,13,14,15"
export GGML_SPACEMIT_BACKEND=1
llama-cli -m modelB.gguf --device SPACEMIT0 -t 4 ...
```

> 上面的核编号只是示例。实际编号请以平台后端日志中的 `preferred core ids` / 系统 `nproc` 为准，**不要照抄**。

### 8.3 多路

- 每路必须运行在**不同核**上；
- 总路数不超过后端 worker 池大小（见 3.5），多路时按可用核数平均分配；
- 每路分到的核数决定线程配置：每路仅 2~4 核时用 `-t 1` 即可（prefill 已接近满配水平，见 3.5）；
- 与 ONNX Runtime（视觉，见第 10 章）混跑时，ORT 侧用 `SPACEMIT_EP_INTRA_THREAD_NUM` / `SPACEMIT_EP_INTRA_THREAD_AFFINITY` 绑定互不重叠的核。

### 8.4 残留与清理

- 推理程序异常退出可能残留 TCM/核占用，表现为后续推理报错或变慢；
- 用 `pkill -9 llama-server` / `pkill -9 llama-cli` 清理；仍异常则重启设备；
- 启动新推理前先 `pkill` 是稳妥做法（llmchat 的启动命令即如此）。

| 现象                                                                                                  | 原因                                                    | 处理                                                                 |
| ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------- | -------------------------------------------------------------------- |
| `llama-cli --list-devices` 输出 `Available devices:` 为空                                             | 未设置`GGML_SPACEMIT_BACKEND=1`                         | 设置后重试；注意变量是进程级的，必须在启动命令的同一 shell 中 export |

| 指定了`--device SPACEMIT0` 但速度没变化                                                               | 未设置环境变量 → 设备不存在自动回退；或`-ngl 0`        | 检查`dev` 列/`SPACEMIT compute buffer size` 日志；设置 `-ngl -1`     |
| `llama-bench` 未指定 `-dev` 时 `backend` 列也显示 `SPACEMIT`                                          | 后端栈标识，与是否指定设备无关                          | 需要明确设备时加 `-dev SPACEMIT0`，`dev` 列会显示该设备              |
| 运行时报`cannot open shared object file` / `undefined symbol`                                         | 自编译程序未设置`LD_LIBRARY_PATH`，或只拷贝了启动器     | `export LD_LIBRARY_PATH=/system/lib64:/system/lib`；保留 `-impl.so`  |
| 交叉链接报`undefined reference to symbol 'ggml_backend_dev_memory'` + `DSO missing from command line` | 只写了`-lllama -lggml`                                  | 追加`-lggml-base`（见 6.8）                                          |
| 链接报`libspert.so.1 ... not found` 或 `undefined reference to spert::detail::...`                    | 链接期静态解析共享库依赖                                | 加`-Wl,--allow-shlib-undefined`（运行时由系统库目录解析）            |

| 输出为空 / 只有思考内容 / 界面空白气泡                                                                | 思考模型把预算烧在`reasoning_content`                   | `--reasoning off`（或 `--reasoning-budget 0`）                       |
| 报`exceed_context_size_error`                                                                         | 提示词长度超过`--ctx-size`                              | 提高`--ctx-size`（llmchat 用 15360，实测提示词约 5192 token）        |

| 应用内比命令行慢 10~20 倍，CPU 600%+                                                                  | 频繁 spawn 子进程（runCmd/curl）把 FFRT 线程池占满      | 健康检查/对话改`@ohos.net.http`；拉起命令用 `exec`（见 7.5）         |
| UI 卡死/被 FreezeDetector 杀                                                                          | `ChildProcess` 对象变成不可达，finalizer 同步 `waitpid` | 存活期间一直持有引用；按名字 pkill，不用 pid 当句柄                  |
| 双路推理都异常                                                                                        | 抢同一批核 / TCM 未释放                                 | 用`SPACEMIT_PERFER_CORE_ID` 绑不同核；`pkill` 后重试                 |
| 性能数字抖动大（如 tg 27 vs 42）                                                                      | 同机并发推理/渲染抢内存带宽，或频率波动                 | 空载、单路、多跑`-r`；不要在跑 bench 时开第二路                      |
| 视觉模型用`AppendExecutionProvider(so, "SpaceMIT", ...)` 报 `Unknown provider name 'SpaceMIT'`        | SpaceMIT EP 不是 ORT 内置 provider                      | 改用`OrtSessionOptionsSpaceMITEnvInit()`（见 10.2）                  |

| 中文输出乱码                                                                                          | 多为通过 hdc/终端传参时的编码问题，非库问题             | 应用内用 UTF-8 字符串；API 请求体明确 charset                        |
| `hdc` 输出 `[1][..] Not support std mode`                                                             | hdc 客户端噪声                                          | 忽略                                                                 |

## 10. 视觉模型推理（ONNX Runtime + SpaceMIT EP）

视觉模型（检测/分割/分类/CLIP 等）走 ONNX Runtime，通过 **SpaceMIT Execution Provider（EP）** 加速。本章给出正确的接入方式与模型选用原则。

### 10.1 为什么不能用 AppendExecutionProvider

SpaceMIT EP **不是** ONNX Runtime 内置 provider。用 ORT 的通用注册接口会直接失败：

```c
/* ❌ 错误用法：会报 Unknown provider name 'SpaceMIT' */
OrtSessionOptionsAppendExecutionProvider(so, "SpaceMIT", NULL, 0);
```

原因：`SessionOptionsAppendExecutionProvider` 只认 ORT 内置的 provider 名（CPU/CUDA/CoreML 等），第三方 EP 需要通过各自的注册函数或 provider 库显式加载。

### 10.2 正确注册方式

**这段在做什么**：创建 session options，用 SpaceMIT 专用入口注册 EP，再创建 session；之后 `Run()` 即由 EP 加速执行。

```c
#include "onnxruntime_c_api.h"
#include "spacemit_ort_env_c_api.h"

const OrtApi * api = OrtGetApiBase()->GetApi(ORT_API_VERSION);

OrtEnv * env = NULL;
api->CreateEnv(ORT_LOGGING_LEVEL_WARNING, "vision", &env);

OrtSessionOptions * so = NULL;
api->CreateSessionOptions(&so);

/* 关键一步：用专用入口注册 SpaceMIT EP（后三个为保留参数，当前传 NULL, NULL, 0） */
OrtSessionOptionsSpaceMITEnvInit(so, NULL, NULL, 0);

OrtSession * sess = NULL;
api->CreateSession(env, "model.q.onnx", so, &sess);   /* 之后 Run 即由 EP 加速 */
```

**关键点**：

- 头文件是 `spacemit_ort_env_c_api.h`（不是 ORT 自带头文件），必须随 SDK 提供；
- 注册成功后 `Run()` 无需改任何代码，算子会自动调度到 EP；
- 若同时注册了其它 EP，注意 provider 的优先级顺序，避免落到 CPU；
- 忘记调用 `OrtSessionOptionsSpaceMITEnvInit()` 时不会报错，但会**静默跑在 CPU 上**——这是“视觉模型没加速”的第一排查点。

### 10.3 编译与链接

链接时需要**同时**链接 ORT 与 EP 库，缺一不可（EP 库提供 `OrtSessionOptionsSpaceMITEnvInit` 符号）：

```sh
$CC -std=c11 -O2 -Wall 
    -I "$ORT_INC" -I "$EP_INC" 
    vision_demo.c 
    -L "$LIB" -lonnxruntime -lspacemit_ep 
    -Wl,--allow-shlib-undefined 
    -Wl,-rpath-link,"$LIB" 
    -o vision_demo
```


| 依赖                       | 作用                                              |
| -------------------------- | ------------------------------------------------- |
| `libonnxruntime.so`        | ONNX Runtime 运行时（`OrtGetApiBase` 等）         |
| `libspacemit_ep.so`        | SpaceMIT EP（`OrtSessionOptionsSpaceMITEnvInit`） |
| `onnxruntime_c_api.h`      | ORT 官方 C API                                    |
| `spacemit_ort_env_c_api.h` | SpaceMIT EP 注册入口                              |

**说明**：若链接报 `undefined reference to OrtSessionOptionsSpaceMITEnvInit`，就是漏了 `-lspacemit_ep`。

### 10.4 模型选用原则


| 模型格式          | 建议        | 说明                                     |
| ----------------- | ----------- | ---------------------------------------- |
| `.q.onnx`（量化） | ✅**首选**  | 量化后算子能完整映射到 EP，加速比最高   |
| `.fp16.onnx`      | ✅ 可用     | 次优，多数视觉模型加速明显               |
| `.onnx`（fp32）   | ⚠️ 不推荐 | 大量算子回退 CPU，**几乎无加速**         |

**实测**（YOLOv8n）：fp32 原始模型只有 **1.23x** 加速，而量化版达到 **24.7x**。因此拿到 fp32 模型时应先做量化（或找官方 `.q.onnx` 版本），再评估 EP 收益。

> 选型顺序：先确认模型有量化/fp16 版本 → 再对比 EP 与 CPU 的端到端耗时 → 最后决定是否上线 EP。

### 10.5 与 LLM 混合部署

同一台设备上同时跑 `llama-server`（语言模型）与 ONNX 视觉模型时：

- 两者共享同一批核，**必须分组绑核**：LLM 侧用 `SPACEMIT_PERFER_CORE_ID`，ORT 侧用 `SPACEMIT_EP_INTRA_THREAD_NUM` / `SPACEMIT_EP_INTRA_THREAD_AFFINITY`，两组核不重叠；
- 单独测各自性能，避免并发干扰导致误判（见 3.5 第 4 条）；
- 视觉模型推理通常耗时短、LLM 生成长，建议把视觉放在 LLM 空闲间隙执行，减少争抢。

## 11. 多模态（VLM）推理

VLM 是**唯一可以像语言模型一样用 `llama-server` 一条命令跑起来**的非纯文本类别，
不需要自己写 C 代码。它的结构与纯 LLM 的区别只在于多了一个视觉编码器。

### 11.1 模型包结构

```text
fastvlm-mm-0.5b-q4_1/
├── config.json                    # 指明 text_model 与 vision_model 两个 model_path
├── fastvlm-text-0.5B-Q4_1.gguf    # 文本主干（GGUF）
└── fastvlm_vision.f16.onnx        # 视觉编码器（ONNX，走 SpaceMIT EP）
```

`config.json` 内容很短，关键就是两个路径：

```json
{
  "architectures": ["LlavaQwen2ForCausalLM"],
  "vision_model": { "model_path": "fastvlm_vision.f16.onnx" },
  "text_model":   { "model_path": "fastvlm-text-0.5B-Q4_1.gguf", "hidden_size": 896 }
}
```

> 如果模型包只有 `mmproj-*.gguf`、没有 `config.json` + ONNX 视觉编码器，
> 就只能用 `mtmd` 后端，**视觉编码器不经 EP 加速**。

### 11.2 启动服务

```bash
# 临时目录必须可写：SMT 后端推理时要写临时文件，根文件系统的 /tmp 是只读的
export TMPDIR=/data/local/tmp; export TMP="$TMPDIR"; export TEMP="$TMPDIR"

llama-server -m fastvlm-text-0.5B-Q4_1.gguf 
  --vision-backend smt --smt-config-dir . 
  --host 127.0.0.1 --port 8071 -t 8 -tb 8 --reasoning off
```

参数说明：

- `--vision-backend {auto|mtmd|smt}`：`smt` 才启用 SpaceMIT EP；`auto` 由程序自行判断。
- `--smt-config-dir <dir>`：`config.json` 所在目录。
- `-tb 8`：批处理线程数，图像预填充阶段受益明显。
- `--reasoning off`：关掉思考链，减少无谓 token。

启动成功的判据（日志中出现这几行即可确认 EP 生效）：

```text
[media-worker] backend 'smt' stage 'smt_vision_init' begin
[SMT][vision] Spacemit EP enabled (, SPACEMIT_EP_INTER_THREAD_NUM=1, SPACEMIT_EP_INTRA_THREAD_NUM=4)
[SMT][vision] warmup ONNX session for LlavaQwen2ForCausalLM
[media-worker] backend 'smt' stage 'smt_vision_init' end
```

### 11.3 调用：OpenAI 兼容接口

图片转成 base64 data URI，放进 `image_url`，其余与纯文本对话一致：

```json
POST /v1/chat/completions
{
  "messages": [{
    "role": "user",
    "content": [
      { "type": "image_url", "image_url": { "url": "data:image/png;base64,<BASE64>" } },
      { "type": "text", "text": "请描述这张图片" }
    ]
  }],
  "max_tokens": 32,
  "stream": true
}
```

注意 `content` 是**数组**（不是字符串），图片项在前、文本项在后，顺序与官方 demo 一致。

### 11.4 常见问题


| 现象                                          | 原因                                                    | 解决                                             |
| --------------------------------------------- | ------------------------------------------------------- | ------------------------------------------------ |
| 图像推理阶段失败 / 报临时文件错误             | `TMPDIR` 指向了只读的 `/tmp`                            | 改成可写目录（如`/data/local/tmp`）并 `mkdir -p` |
| 日志里没有`[SMT][vision] Spacemit EP enabled` | `--vision-backend` 不是 `smt`，或模型包缺 `config.json` | 确认参数与模型包结构                             |
| 报`control character U+000A must be escaped`  | base64 里带了换行                                       | 用`base64 -w0` 生成单行                          |
| 视觉不慢但生成很慢                            | 生成阶段受内存带宽约束，与纯 LLM 同理                   | 换更小模型或更低比特量化                         |

### 11.5 ASR：用与 VLM 相同的方式调用

ASR 与 VLM 共用同一套 SMT 媒体后端，**命令行结构完全一致**，只是 `config.json`
里的键从 `vision_model` 换成 `audio_model`：


| 类别 | `config.json` 中的编码器键                                                        |
| ---- | --------------------------------------------------------------------------------- |
| VLM  | `vision_model.model_path`                                                         |
| ASR  | `audio_model.encoder_model_path`，或 `frontend_model_path` + `backend_model_path` |

因此启动参数不变：

```bash
export TMPDIR=/data/local/tmp; export TMP="$TMPDIR"; export TEMP="$TMPDIR"
export GGML_SPACEMIT_BACKEND=1

llama-server -m Qwen3-ASR-0.6B-text-q40.gguf 
  --vision-backend smt --smt-config-dir . 
  --host 127.0.0.1 --port 8076 -t 8 -tb 8 --reasoning off
```

> `Gemma4` 的 `config.json` 只描述 `audio_model`，不含 gguf 路径，
> 此时 `-m` 需手工指定目录下的文本主干 gguf。

启动后日志应出现音频编码器的 EP 启用信息：

```text
[media-worker] backend 'smt' stage 'smt_audio_init' begin
[SMT][audio] Spacemit EP enabled for frontend (, SPACEMIT_EP_INTRA_THREAD_NUM=4, SPACEMIT_EP_INTER_THREAD_NUM=1)
[SMT][audio] Spacemit EP enabled for backend (, SPACEMIT_EP_INTRA_THREAD_NUM=4, SPACEMIT_EP_INTER_THREAD_NUM=1)
[SMT][audio] warmup ONNX sessions for Qwen3ASRForConditionalGeneration
```

调用时把音频转 base64，用 `input_audio` 类型：

```json
POST /v1/chat/completions
{
  "messages": [{
    "role": "user",
    "content": [
      { "type": "input_audio", "input_audio": { "data": "<BASE64>", "format": "wav" } },
      { "type": "text", "text": "请转写这段音频。" }
    ]
  }],
  "max_tokens": 64,
  "temperature": 0,
  "stream": false
}
```

转写结果在 `choices[0].message.content`，例如
`language Chinese<asr_text>请帮我把这份文档翻译成英文，然后发到我的邮箱。`

性能参考：6 秒中文语音，Qwen3-ASR 端到端 1831 ms（**RTF 0.11**），
Gemma4-ASR 2462 ms（RTF 0.48）。RTF = 处理耗时 / 音频时长，小于 1 即快于实时。

> 注意：`/tmp` 在只读根分区上，若不处理会在 `smt_encode_media` 阶段报
> `failed to create temp file`。做法见 11.4 第 1 行。

### 11.6 TTS：同程序、独立模式，用 `/v1/audio/speech`

TTS 也用 `llama-server`，但走**独立的 TTS 模式**，与 VLM/ASR 有三点不同：

1. **不能带 `-m`**（会报 `TTS server mode cannot be combined with an LLM model`）；
2. 需要 `--tts-speaker-file` 指定音色文件；
3. 接口是 `POST /v1/audio/speech`，**不是** `/v1/chat/completions`（后者返回 404）。

```bash
export TMPDIR=/data/local/tmp; export TMP="$TMPDIR"; export TEMP="$TMPDIR"
# 注意：不要设 GGML_SPACEMIT_BACKEND=1，见下方说明

llama-server --smt-config-dir /data/models/qwen3-tts-0.6b 
  --tts-speaker-file /data/models/qwen3-tts-0.6b/default.spk.bin 
  --host 127.0.0.1 --port 8106 -t 8 -tb 8
```

启动成功的判据：

```text
[media-worker] backend 'smt-tts' stage 'smt_tts_init' begin
[media-worker] backend 'qwen3-tts-talker' stage 'initialize' begin
[media-worker] backend 'qwen3-tts-talker' stage 'initialize' end
I srv run_tts_serv: TTS media backend 'qwen3-tts' is listening on http://127.0.0.1:8106
```

调用示例：

```bash
curl -X POST http://127.0.0.1:8106/v1/audio/speech 
  -H 'Content-Type: application/json' 
  -d '{"model":"qwen3-tts","input":"你好，这是一段语音合成测试。","voice":"default"}' 
  -o out.wav
```

返回体直接是 **24 kHz / 16 bit / 单声道 WAV**（以 `RIFF....WAVE` 开头）。

### 11.7 TTS 的 EP 加速要点

**不要对 TTS 设 `GGML_SPACEMIT_BACKEND=1`**。实测该变量会把 talker 主干卸载到 A100，
而 TTS 是逐帧自回归、带宽受限的负载，卸载后反而变慢（4.21 s → 9.05 s）。

TTS 真正值得加速的是**声码器**。组件级实测（ONNX Runtime 单次推理）：

| 组件 | CPU | SpaceMIT EP | 加速比 | 建议 |
| --- | ---: | ---: | ---: | --- |
| `codec-decoder-t50-q.onnx` | 12513 ms | 946.68 ms | **13.2x** | **应放 EP** |
| `text-embed-proj.onnx` | 1.77 ms | 3.88 ms | 0.46x | 留在 CPU |

`codec-decoder` 是卷积/上采样密集结构，与视觉 CNN 同类，正是 AI 阵列的强项；
`text-embed-proj` 是查表类小算子，EP 的调度开销超过收益。

需要注意：当前版本的 TTS 服务进程只映射了 `talker-q8_0.gguf`、`code-predictor-q4_0.gguf`、
`qwen3-tts-aux.gguf`，**未加载 `codec-decoder-t50-q.onnx`**（声码器内置于 GGUF 路径、走 CPU）。
要获得上述 13.2x 收益，二选一：

- 等官方在 TTS 路径中接入 ONNX 声码器 + SpaceMIT EP；
- 或由应用层把该 ONNX 用第 10 章的方式单独注册到 SpaceMIT EP，自行串联。

`config.json` 里的 `tts_model.ep_config` 是给 EP 侧编码器用的，
与 `GGML_SPACEMIT_BACKEND` 环境变量是两套独立开关，不要混用。
