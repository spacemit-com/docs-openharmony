# SpaceMIT K3 模型性能实测对比

> 基于 **K3 的 OpenHarmony 6.1 LTS 实测数据**整理。

---

## 1. 结论摘要

### 1.1 库版本

本次测试使用的库版本（设备当前安装版本）：

| 组件 | 版本 |
| --- | --- |
| `libllama.so` | `0.0.10056` |
| ggml | `0.16.0` |
| 构建 | `51c81f90f (10056)` |
| ONNX Runtime | `1.24.2+spacemit.a1` |
| SpaceMIT EP | `2.0.7` |

### 1.2 AI 核的启用方式

K3 由 **8 个 X100 通用核 + 8 个 A100 AI 核** 组成。系统内置的 llama.cpp 带有 SpaceMIT
定制后端，两条推理链路都可以把算子调度到 A100 AI 核上：

```sh
export GGML_SPACEMIT_BACKEND=1
llama-bench -m model.gguf -t 8 -p 128 -n 128 -dev SPACEMIT0
```

> **关于 `GGML_SPACEMIT_BACKEND=1` + `--device SPACEMIT0`**：这是**使用新版库、
> 并显式把算子派发到 A100 AI 核**的推荐写法，**并不是**"只有这样才启用 AI 核加速"。
>
> **实测澄清（重要）**：不设置 `GGML_SPACEMIT_BACKEND` 时，**A100 AI 核同样在工作**。
> 用 `/proc/stat` 采样 `Qwen3-0.6B` 推理期间的 16 个逻辑核：cpu8–cpu15（8 个 A100）持续
> **99–100% 满载**，cpu0–cpu7（8 个 X100）合计仅约 13%；`llama-bench` 的 `backend` 列也显示 `SPACEMIT`。
> 因此**不能凭 `dev` 列为空就断定"没用 AI 核"**——它只反映未显式指定设备名。
>
> **三种配置实测对比**（`Qwen3-0.6B-Q4_0`，`-t 8 -p 128 -n 128 -r 3`）：
>
> | 配置 | `dev` 列 | pp128 | tg128 | A100 占用 |
> | --- | --- | ---: | ---: | --- |
> | 不设 env、不传 `-dev` | 空 | 503.86 | 40.84 | 99–100% |
> | 设 env、不传 `-dev` | 空 | 412.39 | 23.02 | 99–100% |
> | 设 env + `-dev SPACEMIT0` | `SPACEMIT0` | 499.29 | 42.06 | 99–100% |
>
> 三者都在用 AI 核，但**设了 env 却不指定设备**时性能明显下降（pp 降至 82%、tg 降至 55%），
> 因为设备被发现后部分算子会被调度到 X100 侧。所以推荐写法是**两者都给**：
> `GGML_SPACEMIT_BACKEND=1` **并且** `--device SPACEMIT0`。

### 1.3 性能结论（要点）

**视觉模型是 AI 核收益最大的场景**，语言模型则因负载而异：

1. **视觉/CNN 类模型：AI 核带来显著的提速**，是本次测试中收益最显著的一类。
   18 个成对模型中 14 个获得 3x 以上加速，最高 **28.0x**：
   典型如 ResNet50（28.0x）、YOLOv8s（24.7x）、YOLOv11n（14.8x）、MobileNetV2（15.3x）。
   这类模型算力密集、以稠密卷积为主，正是 AI 阵列的强项。

2. **语言模型：难有统一结论**，需按模型与量化方式逐一实测。
   Q4_0/Q4_K_M 类模型在两侧接近；Q8_0 量化与 MoE 结构的 decode 通常偏低（见 6.1）。

3. **个别模型在 AI 核上反而更慢**，选型时需注意：
   - 非量化（fp32）视觉模型：YOLOv8n 原始 ONNX 仅 1.23x；而同族量化版 YOLOv8s.q 达 24.7x，
     可见差距主要来自量化而非网络规模；
   - Q8_0 量化的语言模型：Qwen3-1.7B-Q8_0 的 decode 相对偏低；
   - MoE 结构语言模型：LFM2-24B、Qwen3-30B-A3B 的 decode 受带宽约束。

4. **VLM / ASR / TTS 三类都由 `llama-server` 承载**，共用 SMT 媒体后端。
   VLM 视觉预填充 134–8061 ms（取决于分辨率与编码器体积）；ASR 最优 RTF **0.38**
   （Fun-ASR q4km 与 Qwen3-ASR-0.6B），TTS 合成 4.2 s 音频约 4.21 s。

5. **量化的影响远大于模型规模**：ASR 从 fp32 到 q4km/q40 提速 7–11 倍；
   TTS 的加速点在声码器（EP 下 13.2x），而非 talker 主干。

## 3. 测试方式

### 3.1 语言模型（llama.cpp）

```sh
export GGML_SPACEMIT_BACKEND=1
llama-bench -m <model.gguf> -t 8 -p 128 -n 128 -fa 1 -ub 128 \
    --load-mode mmap -dev SPACEMIT0 -r 3
```

- `pp128`：128 token 提示下的 prefill 吞吐（token/s）
- `tg128`：128 token 生成的吞吐（token/s）
- 每组取 3 次重复的均值

对比组：

- **推荐路径**：`GGML_SPACEMIT_BACKEND=1` + `-dev SPACEMIT0`
- **对照组**：不设 `GGML_SPACEMIT_BACKEND`、不传 `-dev`（实测其 A100 占用与设置后相同，见 1.2；性能接近）

### 3.2 视觉模型（ONNX Runtime）

用自研 `ort_bench` 直接加载 ONNX，对比：

- `-e spacemit`：SpaceMIT EP（A100）
- `-e cpu`：ORT CPU EP

每组 18 次取均值，单位为单次推理耗时（ms）与 FPS。

### 3.3 其他模型

- **VLM / ASR**：`llama-server -m <gguf> --vision-backend smt --smt-config-dir <dir> -t 8 -tb 8`
- **TTS**：`llama-server --smt-config-dir <dir> --tts-speaker-file <spk>`（不加 `-m`）
- 编码器启用 EP 的判据是日志出现 `[SMT][vision] Spacemit EP enabled` /
  `[SMT][audio] Spacemit EP enabled`
- `/tmp` 位于只读根分区，需先 `mount -t tmpfs -o size=256m tmpfs /tmp` 或指定可写的
  `TMPDIR`/`TMP`/`TEMP`，否则编码器写临时文件失败

## 4. 视觉模型性能

条件：ORT + SpaceMIT EP vs ORT CPU EP，合成输入，18 次取均值。
加速比 = CPU 耗时 / EP 耗时。

| 模型 | 输入形状 | EP 耗时 | EP FPS | CPU 耗时 | CPU FPS | 加速比 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| mobilenet_v2.q | 1×3×224×224 | 4.07 ms | 245.6 | 62.09 ms | 16.1 | 15.25x |
| resnet50.q | 1×3×224×224 | 14.16 ms | 70.6 | 396.90 ms | 2.5 | **28.03x** |
| yolov8n-pose.q | 1×3×640×640 | 22.01 ms | 45.4 | 409.25 ms | 2.4 | 18.59x |
| yolo11n.q | 1×3×640×640 | 24.40 ms | 41.0 | 361.59 ms | 2.8 | 14.82x |
| yolov8n-seg.q | 1×3×640×640 | 25.82 ms | 38.7 | 493.75 ms | 2.0 | 19.13x |
| yolo26n.q | 1×3×640×640 | 30.86 ms | 32.4 | 342.97 ms | 2.9 | 11.11x |
| yolov8s.q | 3×640×640 | 39.97 ms | 25.0 | 986.26 ms | 1.0 | 24.68x |
| yolo11s.q | 3×640×640 | 43.07 ms | 23.2 | 861.13 ms | 1.2 | 19.99x |
| yolo26s.q | 3×640×640 | 53.03 ms | 18.9 | 855.19 ms | 1.2 | 16.13x |
| mobileseg_mobilenetv2_cityscapes_1024x512.q | 1×3×512×1024 | 79.76 ms | 12.5 | 599.27 ms | 1.7 | 7.51x |
| yolov8m.q | 3×640×640 | 108.50 ms | 9.2 | 2421.73 ms | 0.4 | 22.32x |
| deimv2n.fp16 | 1×3×640×640 | 112.69 ms | 8.9 | 284.40 ms | 3.5 | 2.52x |
| rfdetr-nano.fp16 | 1×3×640×640 | 129.60 ms | 7.7 | 1061.76 ms | 0.9 | 8.19x |
| pp_liteseg.q | 1×3×512×1024 | 130.96 ms | 7.6 | 1174.94 ms | 0.9 | 8.97x |
| vit_b_16.fp16 | 1×3×224×224 | 139.47 ms | 7.2 | 947.49 ms | 1.1 | 6.79x |
| yolov8n（fp32 原始） | 1×3×640×640 | 227.17 ms | 4.4 | 280.49 ms | 3.6 | 1.23x |
| PP-OCRv5_mobile_det | 1×3×960×960 | 580.63 ms | 1.7 | 473.34 ms | 2.1 | 0.82x |
| yoloe-v8s-seg.dynq | 1×3×640×640 | 891.12 ms | 1.1 | 1203.28 ms | 0.8 | 1.35x |

### 4.1 解读

1. **量化是收益的前提**：同族对比 YOLOv8n（fp32）仅 1.23x，而量化版 YOLOv8s.q 达 24.68x。
   EP 的量化算子在 AI 阵列上有专门优化，非量化路径反而要额外做数据搬运。
2. **中等规模模型收益最高**：ResNet50、YOLOv8s/m、YOLO11s 等集中在 14–28x 区间，
   说明 AI 阵列在稠密卷积上有明显算力优势，且模型足够大时能摊薄调度开销。
3. **小模型受固定开销支配**：MobileNetV2 绝对延迟仅 4.1 ms，加速比仍有 15.3x；
   但若模型更小，EP 的固定调度开销会开始占比，加速比将回落。
4. **两个例外**：PP-OCRv5_mobile_det 的 EP 反而慢 18%（0.82x），YOLOE-v8s-seg 仅 1.35x。
   这类含大量后处理或特殊算子的模型建议实测后再决定是否启用 EP。

  14 个模型达到 3x 以上加速，中位数为 **14.82x**。

## 5. 多模态与语音模型性能

除纯语言模型和纯视觉模型外，model zoo 还提供多模态（VLM）、语音识别（ASR）与语音合成
（TTS）模型。这三类**共用同一套 SMT 媒体后端**，都可由 `llama-server` 承载，
区别在于启动参数与 `config.json` 的键名。

### 5.1 统一的调用方式

三类的模型包都是「`config.json` + GGUF 文本主干 + ONNX 编码器/声码器」结构，
`config.json` 里都带 `ep_config` 用于指定 SpaceMIT EP 的线程配置：

| 类别 | `config.json` 中的键 | 启动方式 |
| --- | --- | --- |
| VLM | `vision_model.model_path` | `-m <gguf> --vision-backend smt --smt-config-dir <dir>` |
| ASR | `audio_model.encoder_model_path`，或 `frontend_model_path`+`backend_model_path` | 同上（与 VLM 完全一致） |
| TTS | `tts_model.*`（talker / code-predictor / codec-decoder） | `--smt-config-dir <dir> --tts-speaker-file <spk>`，**不加 `-m`** |

```bash
# /tmp 在只读根分区上，必须让临时目录可写
mount -t tmpfs -o size=256m tmpfs /tmp

export TMPDIR=/data/local/tmp; export TMP="$TMPDIR"; export TEMP="$TMPDIR"

# VLM / ASR
export GGML_SPACEMIT_BACKEND=1
llama-server -m <文本主干.gguf> \
  --vision-backend smt --smt-config-dir <含 config.json 的目录> \
  --host 127.0.0.1 --port 8071 -t 8 -tb 8 --reasoning off

# TTS（注意：不能带 -m，否则报 "TTS server mode cannot be combined with an LLM model"）
llama-server --smt-config-dir <含 config.json 的目录> \
  --tts-speaker-file <dir>/default.spk.bin \
  --host 127.0.0.1 --port 8106 -t 8 -tb 8
```

编码器启用 EP 时，日志会给出对应证据：

```text
# VLM
[SMT][vision] Spacemit EP enabled (, SPACEMIT_EP_INTRA_THREAD_NUM=4, SPACEMIT_EP_INTER_THREAD_NUM=1)
# ASR
[SMT][audio] Spacemit EP enabled for frontend
[SMT][audio] Spacemit EP enabled for backend
# TTS
[media-worker] backend 'smt-tts' stage 'smt_tts_init' begin
[media-worker] backend 'qwen3-tts-talker' stage 'initialize' begin
I srv run_tts_serv: TTS media backend 'qwen3-tts' is listening on http://127.0.0.1:8106
```

两个通用坑：`/tmp` 只读会让编码器写临时文件失败（`failed to create temp file`）；
`--vision-backend` 必须是 `smt`，用 `mtmd` 时编码器不走 AI 核。

### 5.2 VLM 全量实测

测试图 448×448 PNG，`-t 8 -tb 8`，`--vision-backend smt`，生成上限 32 token：

| 模型 | 参数规模 | 视觉编码器 | 视觉预填充 | 生成速度 |
| --- | --- | --- | ---: | ---: |
| LFM2.5-VL-450M | 450M | f16 ONNX 256² | **134 ms** | 58.5 t/s |
| fastvlm-0.5B | 0.5B | f16 ONNX | 280 ms | 25.3 t/s |
| LFM2.5-VL-1.6B | 1.6B | f16 ONNX | 355 ms | 27.3 t/s |
| MiniCPM-V-4.6 | — | fp16 ONNX | 797 ms | 12.1 t/s |
| Qwen3.5-VL-0.8B | 0.8B | f16 ONNX 768 | 2687 ms | 12.2 t/s |
| Qwen3.5-VL-2B | 2B | f16 ONNX 768 | 3444 ms | 14.6 t/s |
| Qwen3.5-VL-4B | 4B | f16 ONNX 768 | 8061 ms | 3.3 t/s |
| Qwen3VL-4B（mtmd 路径） | 4B | F16 mmproj（**不走 EP**） | — | 3.4 t/s |

要点：

- **Qwen3.5 系列随规模线性劣化**：0.8B → 2B → 4B 的视觉预填充为 2687 / 3444 / 8061 ms，
  4B 的编码器（636 MB）比 0.8B（192 MB）重 3.3 倍，且均用 768 分辨率。
- **视觉预填充差异主要来自分辨率与编码器体积**，不只看文本模型大小：
  LFM2.5-VL-1.6B（355 ms）的快，来自 256² 输入。
- 只有 mmproj、没有 `config.json`+ONNX 的包装（如独立 Qwen3VL-4B）只能用 `mtmd`，
  视觉编码器不参与 AI 核加速，生成速度明显偏低。

### 5.3 ASR 全量实测

测试音频为 16 kHz 单声道中文语音，时长 **5995 ms**，`[SMT][audio]` 路径，
耗时取服务端 `total time`（含编码与生成）：

| 模型 | 量化 | 音频编码器 | 音频预填充 | 总耗时 | **RTF** |
| --- | --- | --- | ---: | ---: | ---: |
| Fun-ASR-Nano-2512 | q4km | EP（frontend+backend） | **711 ms** | 2302 ms | **0.38** |
| Qwen3-ASR-0.6B | q40 | EP（frontend+backend） | 656 ms | 2270 ms | **0.38** |
| Qwen3-ASR-1.7B | q40 | EP（frontend+backend） | 997 ms | 3295 ms | 0.55 |
| Qwen3-ASR-1.7B | q4km | EP（frontend+backend） | 1251 ms | 4142 ms | 0.69 |
| Gemma4-ASR-E2B | q40 | ORT CPU（见下） | 2881 ms | 5303 ms | 0.88 |
| Fun-ASR-Nano-2512 | fp32 | EP（frontend+backend） | 5151 ms | 7778 ms | 1.30 |
| Qwen3-ASR-1.7B | fp32 | EP（frontend+backend） | 11390 ms | 16996 ms | 2.83 |

要点：

- **量化是 ASR 的首要变量**，远超模型规模的影响：
  Qwen3-ASR-1.7B 的 fp32 音频预填充 11390 ms，q40 只要 997 ms（**11.4x**）；
  Fun-ASR 的 fp32 5151 ms，q4km 只要 711 ms（**7.2x**）。
- **0.6B 与 1.7B 的差距不大**（RTF 0.38 vs 0.55），0.6B 性价比更高。
- **Gemma4-ASR 的音频编码器回退到 CPU**（日志 `[SMT][audio] using ORT CPU for Gemma4 encoder`）。
  单独用 ONNX Runtime 测同一 `audio_encoder.q.onnx`：EP 106.40 ms、CPU 924.30 ms（8.69x），
  说明该编码器本身能在 AI 核上跑，回退是服务侧实现选择。
- 转写结果均正确（示例音频"请帮我把这份文档翻译成英文，然后发到我的邮箱"）。
- 1.7B 的 `q40` 配置额外启用了线程亲和性
  （`SPACEMIT_EP_INTRA_THREAD_AFFINITY=8;9;10;11`），Qwen3-ASR 与 Fun-ASR 均走原生 SMT 音频路径。

> RTF = 处理耗时 / 音频时长，小于 1 表示快于实时。

### 5.4 TTS 与 EP 加速分析

TTS 同样由 `llama-server` 承载，但走独立的 TTS 模式，接口是 OpenAI 兼容的
`POST /v1/audio/speech`（不是 `/v1/chat/completions`，后者在 TTS 模式下返回 404）：

```json
{"model":"qwen3-tts","input":"你好，这是一段语音合成测试。","voice":"default"}
```

返回 24 kHz / 16 bit 单声道 WAV。实测 `qwen3-tts-0.6b` 合成 4.2 s 音频耗时 **4.21 s**。

**EP 加速的关键发现**：对 TTS 加 `GGML_SPACEMIT_BACKEND=1` 反而**变慢**
（4.21 s → 9.05 s），因为该变量会把 talker 主干卸载到 A100，
而 TTS 逐帧自回归生成的负载形态与语言模型相同、属带宽受限，卸载并无收益。

因此 TTS 的加速点不在 talker 主干，而在**声码器（codec-decoder）**。
组件级实测（ONNX Runtime，单次推理）：

| 组件 | 输入 | CPU | SpaceMIT EP | 加速比 |
| --- | --- | ---: | ---: | ---: |
| `codec-decoder-t50-q.onnx` | codes[1,16,50] | 12513.27 ms | **946.68 ms** | **13.2x** |
| `text-embed-proj.onnx` | input_ids[1,1] | 1.77 ms | 3.88 ms | 0.46x（EP 更慢） |

结论与建议：

1. **优先把 codec-decoder 放到 EP**：它是 TTS 中算力密集的卷积/上采样结构，
   与视觉 CNN 同类，正是 AI 阵列的强项，理论收益 13.2x。
   `text-embed-proj` 是查表类小算子，EP 反而更慢，应留在 CPU。
2. **不要对 TTS 开 `GGML_SPACEMIT_BACKEND=1`**：会误把 talker 主干搬上 A100 导致负优化。
   `config.json` 里 `tts_model.ep_config`（当前为 INTRA=4 / INTER=1）是给 EP 侧编码器用的，
   与 `GGML_SPACEMIT_BACKEND` 是两套独立开关。
3. **当前版本的限制**：实测服务进程只映射了 `talker-q8_0.gguf`、`code-predictor-q4_0.gguf`、
   `qwen3-tts-aux.gguf` 三个 GGUF，**未加载 `codec-decoder-t50-q.onnx`**，
   说明该版本把声码器内置于 GGUF 路径、走 CPU。
   要拿到上面 13.2x 的收益，需要官方在 TTS 路径中接入 ONNX 声码器 + SpaceMIT EP，
   或由应用层自行串联（用第 3 章的 EP 注册方式加载该 ONNX）。

### 5.5 小结

- **VLM / ASR 用同一套 `llama-server --vision-backend smt --smt-config-dir`**，
  换模型只换 `-m` 与目录；TTS 用同一程序但需去掉 `-m` 并加 `--tts-speaker-file`。
- **量化优先于规模**：ASR 从 fp32 到 q40/q4km 可提速 7–11 倍。
- **VLM 的预填充开销由视觉编码器体积与分辨率主导**，Qwen3.5 系列 4B 已达 8 s 量级。
- **TTS 的加速点在声码器而非 talker 主干**，且不可套用 `GGML_SPACEMIT_BACKEND`。

## 6. 语言模型性能

### 6.1 各模型族实测

推荐路径（`GGML_SPACEMIT_BACKEND=1 --device SPACEMIT0`）与对照组的实测数据。
PP128 为 128 token 提示下的 prefill 吞吐，TG128 为 128 token 生成的吞吐（token/s）。

### 6.1.1 Qwen3 系列

| 模型 | 量化 | 参数量 | 体积 | PP128 | TG128 | 对照 PP128 | 对照 TG128 |

### 6.2 线程数与 AI 核的关系

线程数对吞吐的影响（以 `Qwen3.5-2B-Q4_0` 为例，单请求）：

| CPU 线程数 `-t` | PP128 | TG128 |
| ---: | ---: | ---: |
| 1 | 133.00 | 13.06 |
| 2 | 133.71 | 13.16 |
| 4 | 133.62 | 13.19 |
| 8 | 132.77 | 13.19 |

要点：

1. **AI 核吞吐几乎不随 `-t` 变化**（PP 133.00→132.77，TG 13.06→13.19）：
   AI 后端使用固定大小的 worker 池，`-t` 只影响 CPU 侧配合线程，不改变 AI 阵列的并行度。
2. **单线程即可获得高吞吐**：`-t 1` 的 PP≈133、TG≈13，已能满足多数交互场景。
   这对多路并发、只分到少量 CPU 核的场景非常关键：一路 AI 核推理 + 其余核跑业务，
   比多路都挤在通用核上更划算。
3. **调 `-t` 不会让单路 AI 核推理变快**。需要在单路内提升吞吐时，应调模型/量化/`-ub` 等，
   而不是加线程。多路场景的做法见第 7 章。

## 7. 选型建议

| 场景 | 推荐 |
| --- | --- |
| 实时视觉（检测/分割/分类），已量化 | **首选 SpaceMIT EP**，14–28x 提升 |
| 视觉模型为 fp32 原始导出 | 先量化再上 EP，否则收益可能不到 2x |
| OCR / 特殊后处理类视觉模型 | 先实测，PP-OCRv5 在 EP 下反而慢 18% |
| VLM 实时交互 | LFM2.5-VL-450M / fastvlm-0.5B（预填充 <300 ms） |
| VLM 高质量理解 | Qwen3.5-VL-2B（预填充 3.4 s）；4B 需 8 s，仅适合离线场景 |
| ASR 实时转写 | **Fun-ASR q4km 或 Qwen3-ASR-0.6B**（RTF 0.38） |
| ASR 高准确率 | Qwen3-ASR-1.7B q40（RTF 0.55）；避免 fp32（RTF 2.83） |
| TTS | `qwen3-tts-0.6b`，4.2 s 音频约 4.2 s；声码器上 EP 可望再提速（见 5.4） |
| 语言模型 | 按 6.1 实测值选型；优先 Q4_0/Q4_K_M 量化 |

## 8. 局限与未覆盖项

1. 视觉模型仅覆盖检测/分割/姿态/分类/深度等代表性家族，未穷举仓库全部模型。
2. 语言模型未测长上下文（>4K）与多并发吞吐；6.2 的线程扫描为单请求场景。
3. 未测量功耗、温度与长时间稳定性。
4. VLM 覆盖 7 个模型（含 Qwen3.5 0.8B/2B/4B）、ASR 覆盖 7 个变体，均取单张图片/单条音频，
   未测多图、长音频与并发。VLM 未做同模型 CPU 对照（`mtmd` 与 `smt` 的视觉编码器格式不同）。
   TTS 只测了端到端时延与组件级 EP 收益，未做 TTS 路径内启用 EP 的端到端对比。
5. 视觉模型使用合成输入，仅反映算力与内存行为，不代表实际识别精度。
